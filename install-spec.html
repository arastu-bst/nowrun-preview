Getting an app into a session

The card a person sees when they ask ChatGPT for an app: how it decides what to show, what it says, and what it needs from the backend. Approved 15 Sep. This document describes the behaviour; the interactive prototype is the reference for anything not written here.

01 — State model

Three runs, chosen by state, never by a setting

The card is one component. Which of the three runs it performs is derived from two booleans the client must know before it renders.

installed
This app is in this user's nowrun. Persists across conversations.
warm
This app has already been launched in this conversation, so an instance is attached and can be reused. Resets when a new chat starts.
ConditionRunWhat happensGestures
!installed install Card offers to search. On consent: search, find, download, install. Stops at ready. Two
installed && !warm open Card offers to open. Cold session start, then the app. One
installed && warm warm Attaches to the running instance. Same screens, finishes sooner. One
Backend requirement

The plugin must be able to answer “is this app in this user’s nowrun?” before the card renders, not after the person taps. The whole design rests on the card stating where things stand up front. A card that asks first and discovers second cannot be built from this spec.

Install and launch are two separate acts

The install run does not flow into the app. It ends at a ready state with its own Open button. Agreeing to put an app into your nowrun is a different decision from running it, and a browser will not start a stream without a gesture anyway. This is Ambreesh's “app is ready to use, click to launch the app”.

02 — The card before install

App, action, explanation

Vertical order, top to bottom. Nothing is fetched before the button is pressed.

  1. App icon — 22% of card width, 24% corner radius.
  2. App name — no category line, no description.
  3. Primary button — Search and install, full width, pill.
  4. Diagram — ChatGPT, nowrun, three generic app tiles. Static, no animation.
  5. Caption — “nowrun links ChatGPT to the apps you add”.
  6. Attribution — “Powered by nowrun”, pinned to the card floor.

The icon, name and button are grouped tightly (11–12px apart at a 236px card) and the diagram sits ~31px clear of them, so the decision and the explanation read as two separate blocks.

Why there is no decline button

An earlier draft had Not now beside the primary action. It was removed: dismissal is the window’s own close control, and a second button competes with the one that matters. Nothing is fetched until the primary button is pressed, so the consent is still explicit.

What the diagram must not do

The three app tiles are generic glyphs — a plane, a cart, a play mark. They must never be replaced with real third-party app icons. No store, marketplace or distributor is named anywhere in this flow, in either direction. nowrun itself is set in the wordmark, never as a glyph mark.

03 — The install run

Four steps, and one moment

The app icon and name stay exactly where the gate put them. Only what is beneath them changes, so the object you agreed to install is the object you watch install.

StepLabelBadge on the iconLine under the name
1Searching Magnifier, pulsing. A scanner band sweeps across the icon. The search term, mono, with a magnifier
2Found Grey tick. The app exists; nothing is on the device yet. Becomes the publishing company’s name
3Downloading Grey tick, with a progress ring closing around it Publisher
4Installing Tick turns green. Ring gone. Publisher

Found is the argument

It is the only step that gets a flourish, because it is the one that proves nothing was pre-bundled. The icon lifts ~8%, a neutral ring expands from it, the tick lands, the step label pops and brightens, and the query becomes a real publisher name. Everything else on the card holds still. If every step animated, none of them would read as an event.

Do not lose this

The visible search is the entire anti-prebundling argument. If the implementation resolves the app instantly and skips straight to downloading, the flow stops making the point it exists to make. Step 1 must be shown even when the lookup is fast.

The lower half

The diagram holds the lower half for the whole install run and never hands over to the tips carousel. The carousel is not rendered on this run at all.

Where the search term comes from

It is the argument the model passed to search_apps, resolved from what the person said — nobody types it. It is set in the mono face for exactly that reason: it is a value the system is holding, not a field. It must not be drawn as a text input.

04 — Ready, and the second tap

Installed. Ready to use.

App icon with a green tick badge, the app name, the line Installed. Ready to use., and a primary Open {app} button. No diagram, no attribution — the person has already agreed and this screen has one job.

Pressing Open starts the launch run below, on the same card.

05 — The launch run

One bar, and tips

Used for open, for warm, and for the launch that follows an install. Same frame as the install run: app at the top, lower half for content.

  • One indeterminate bar, labelled Starting, looping continuously. Not a three-part step line. Opening an app you already have has no stages worth counting, and a bar that fills in thirds claims progress we cannot know.
  • Tips carousel in the lower half — swipeable, with dots. Auto-advances every 6s.
  • Powered by nowrun at the card floor.
  • No search line, since nothing was searched for.

Live

The app's own screen, streamed. A status strip appears at the card floor — and only here — with a running state and a clock. The strip does not appear on any other screen.

07 — Timing and events

Read this before implementing

Every duration in the prototype is a demo control, not a measurement. In the build, steps must advance on real backend events. The step line is a state indicator, not a timer.

What the client needs to be told

EventCard does
search startedStep 1, magnifier, scanner running
app resolvedStep 2, grey tick, publisher name replaces the query
download startedStep 3, ring begins closing
download progress %Drives the ring. See note below
install startedStep 4, tick turns green
install completeReady screen
session attached / app visibleLive screen, strip and clock appear

The download ring

In the prototype the ring is driven by the step duration. If real download progress is available, use it — that is what the ring is for. If it is not available, the ring must still complete before the tick turns green; never leave it part-drawn on a completed step.

Relative lengths are the claim

The one timing claim the design makes is proportional: install is long, open is shorter, warm is shortest — the prototype runs warm at roughly a third of a cold open. If warm launches are not meaningfully faster in the build, the third run should not ship as a distinct state.

Green means done

Green (#4ea87a) appears exactly twice in the whole flow: the tick once the app is on the device, and the running dot on the live strip. Nothing celebratory is green. The grey tick is #5a625d — a desaturated version of the same green, so the transition stays in one hue family and never passes through a muddy midpoint.

Everything else derives from the ink channel at an alpha, so the card works on either theme without a second palette.

Type

Geist for everything, Geist Mono for values the system is holding — the search term, the step label, the publisher. The distinction is meaningful: mono means “this is data”, not decoration.

The nowrun wordmark is now at weight 500 upright and run at weight 700 with skewX(-10deg). It is a skew on the upright face, not an italic. There is no italic Geist in this design.

Do not ship these

The prototype also contains a ChatGPT sidebar, composer and message chrome, plus the ChatGPT mark outside the diagram. Those exist only to stage the card in a believable window. They are not ours and must not be rebuilt — in the real thing that surface belongs to ChatGPT.

App icons

The two in the prototype are demo bitmaps embedded as base64. In the build they come from the catalogue lookup along with the publisher name. Confirm the lookup returns an icon URL — if it does not, the gate, every install step, the ready screen and the found moment all lose their subject.

Source of truth

The prototype is a single self-contained HTML file with every style, keyframe and SVG inline and no build step. Where this document and the file disagree, the file wins. Read values off it rather than re-deriving them.

11 — Not designed yet

These states exist in the real world and have no design. They will be invented at implementation time unless they are specified first, so please raise them rather than improvise.

Blocking

Failure. There is no error state anywhere in this flow. Not found, download failed, install failed, session could not start, network lost mid-install. At minimum the card needs a failed state per step with a retry, and wording that does not name a store when a search fails.

Ambiguous resolution

The flow assumes search_apps returns exactly one confident match. Two plausible matches, or a vague ask, has no design. Options are a disambiguation state on the card, or the assistant asking in the chat before the card appears — these produce different screens.

First-run login

The first launch of a freshly installed app is where the person hits the app's own sign-in, with a soft keyboard. Today the design treats that launch as identical to every later one. It is the app's screen, not ours, but it is the moment most likely to surprise someone in a demo.

Declining

The decline button was removed, so the only way out is the window close control. What happens in the conversation afterwards — does the assistant offer again? — is undefined.

Second install in one chat

Installing a second, different app in the same conversation shows the diagram again. Whether that is right, or whether it should only ever appear once per person, is not settled.

12 — Open decisions

Small, but each one changes a screen. Worth closing before build starts.

  1. Tips 4 and 5 never surface at the approved pacing. Either cut the list to three, or accept them as depth for people who swipe.
  2. One tip list for every run. The tips were written for a first encounter, but they only appear on launch runs, where the person already owns the app. A second set written for that moment would be seen more and work harder.
  3. Publisher name on the found row. It is the one real-world string in the flow, and it is what makes the result read as something found rather than something bundled. Confirm it is available from the lookup.
  4. Warm state. Ship only if warm launches are measurably faster.
